# 城市托育中心 · 入托评估与接送交接平台

## 原始需求

> 建设城市托育中心入托评估与接送交接平台，可采用 Vue 3、Spring Boot 和 PostgreSQL。家长提交儿童年龄、过敏史、疫苗情况、午睡习惯、如厕能力、常用药、紧急联系人和接送授权人后，平台生成入托评估任务。园长根据班级容量、师幼比、特殊照护需求和家长期望安排班级；保健老师在入托前完成健康评估，确认是否需要过敏餐、临时观察或家长补充资料。每日晨检时，老师记录体温、皮肤、情绪、饮食和携带物品，结果会影响孩子能否入班、是否需要隔离观察、是否通知家长接回。午间照护、喂药、如厕、睡眠和活动伤情都进入同一条在园记录。接送时，前台需要核验授权人、人脸或证件、临时委托和家长留言；若未授权人员到场、孩子发热、药品漏带或班级发生抓咬事件，平台要把老师、保健老师、园长和家长拉到同一事件中处理。离园后，当日照护记录会影响家长沟通、退费争议、风险复盘和后续班级安排。平台还要按班级、儿童、家长和事件形成时间轴，园方处理纠纷时可以看到晨检、照护、接送和沟通是否连续。若同一儿童多次出现异常，系统会提示是否需要调整班级、增加保健观察或约谈家长。

## 原始需求（增量：过敏餐临时替换）

> 增加过敏餐临时替换。厨房发现某类食材缺货或当天菜单含儿童过敏源时，平台先比对儿童档案、替代食材和营养要求，再把替换方案推给保健老师和班级老师确认。家长确认后，厨房出餐、老师分餐和当日饮食记录同步更新；若家长未确认，孩子进入人工照护提示，避免误食。厨房执行后，班级老师在分餐页会看到替代餐标记和家长确认时间，避免交接中只靠口头提醒。

## 技术栈

- **前端**：Vue 3 + Vite + Element Plus + Pinia + Vue Router（构建为静态资源，由后端统一托管）
- **后端**：Spring Boot 3（Java 17）+ Spring Data JPA + Spring Security + JWT
- **数据库**：PostgreSQL 16
- **部署**：多阶段 Dockerfile（非 root 运行 + HEALTHCHECK）+ docker compose 一键启动

## 一键启动（验证方式 = 宿主 docker compose up）

```bash
cp .env.example .env   # 可选；验证环境已注入 CC_PUBLISH_PORT / COMPOSE_PROJECT_NAME
docker compose up -d --build
```

- 应用容器健康检查通过后，访问 `http://localhost:${CC_PUBLISH_PORT}`（默认 3025）。
- 取实际映射端口：`docker compose port app 8080`。
- 数据库仅在 compose 内部网络暴露，应用通过服务名 `db` 访问，不发布到宿主。
- 首次启动自动建表并写入演示账号与演示业务数据（幂等，重启不重复写入）。
- 停止并释放资源：`docker compose down`（加 `-v` 可清空数据重新初始化）。

## 演示数据与推荐体验路径

预置数据：3 个班级（小芽班 1-2 岁、苗苗班 2-3 岁、果果班 3-4 岁）；张乐乐已入托苗苗班（花生过敏、需过敏餐、今日有喂药委托与外婆临时接送委托、今日家长留言）；李朵朵待分班；王豆豆待健康评估；张乐乐近 30 天已有多次发热异常（已生成异常预警）。餐食演示：今日午餐含花生酱（命中张乐乐花生过敏档案，替换单已过保健/班级老师、**待家长确认**）；昨日午餐鲜虾缺货触发的替换单已走完全流程（已分餐）。

1. **入托评估流**：`parent2` 登录可见李朵朵「待分班」→ `director` 在「入托评估任务」分班（对话框展示各班容量/在托/师幼比/带班老师，以及儿童特殊照护与家长期望）→ `health` 在「健康评估」给出结论（可选需过敏餐/临时观察/要求家长补充资料；选补充资料则 `parent2` 在「入托申请」补充后回到待评估）。
2. **过敏餐临时替换流**：`kitchen`「每日菜单」发布菜单（预置今日午餐含花生酱）→「比对受影响儿童」平台自动命中张乐乐（花生）→ 发起替换方案（平台核验替代食材并生成营养比对说明；替代食材含过敏源会被拒绝）→ `health`「替换餐确认」→ `teacher2`「分餐与替换餐」确认 → `parent1`「替换餐确认」同意 → `kitchen`「替换餐执行」出餐 → `teacher2` 分餐页看到**替代餐标记 + 家长确认时间**，点「确认分餐」；出餐/分餐自动写入当日饮食记录（在园照护记录-用餐）与成长时间轴。**家长未确认时**，分餐页整行标红「人工照护 · 禁止发放常规餐」，避免误食。
3. **晨检与在园记录**：`teacher2`「每日晨检」登记张乐乐（体温 ≥37.3℃ 时禁止选入班；该儿童今日有喂药委托，若选“未带药”自动生成药品漏带事件）→「在园照护记录」添加午间照护/喂药/如厕/睡眠/活动伤情（伤情“需关注/严重”自动建事件，抓咬类自动归为抓咬事件）。
4. **接送核验**：`frontdesk`「接送核验」选张乐乐 → 输入「王秀珍」核验 → 命中今日临时委托 → 人脸/证件核验后放行；输入陌生人「李四」核验不通过 →「拒绝并上报」自动创建未授权到场事件。
5. **协同事件**：任一事件详情页中，老师、保健老师、园长、家长（`parent1`）均可留言，园内角色可推进 待处理→处理中→已解决（必填处理结论，用于风险复盘）→已关闭。
6. **时间轴**：「时间轴」页按儿童/班级/事件查看；事件详情页内嵌事件时间轴，可核对晨检、照护、接送、沟通是否连续；家长在「孩子详情 → 成长时间轴」查看自己孩子（含过敏餐替换记录）。
7. **异常预警**：`director`「异常预警」查看系统建议（调整班级/增加保健观察/约谈家长）并填写处理记录；再为张乐乐登记一次异常晨检可观察预警逻辑（同一儿童 30 天内异常 ≥3 次自动生成，存在未处理预警时不重复生成）。

## 主要接口（JWT 鉴权）

- `POST /api/auth/login` 登录；`POST /api/auth/register` 家长注册；`GET /api/dashboard` 角色工作台统计
- `POST /api/applications` 家长提交入托申请（儿童资料+紧急联系人+接送授权人+家长期望）；`POST /api/applications/{id}/assign` 园长分班；`POST /api/applications/{id}/health-assessment` 健康评估；`POST /api/applications/{id}/supplement` 家长补充资料
- `POST /api/attendance/morning-checks` 晨检（发热/异常自动建事件，药品漏带自动建事件）；`POST /api/attendance/care-records` 照护记录（伤情自动建事件）；`GET /api/attendance/daily` 儿童某日完整在园记录
- `POST /api/pickup/verify` 接送身份核验；`POST /api/pickup/records` 放行/拒绝（拒绝自动建未授权到场事件）
- `POST /api/meals/menus` 厨房发布/更新菜单；`GET /api/meals/menus/{id}/affected-children` 平台比对受影响儿童（过敏档案 × 菜单食材）
- `POST /api/meals/substitutions` 厨房发起替换单（平台核验替代食材+生成营养比对）；`POST /api/meals/substitutions/{id}/health-confirm|teacher-confirm|parent-confirm` 保健/班级老师/家长依次确认；`POST .../execute` 厨房出餐、`POST .../serve` 老师分餐（均同步当日饮食记录）；`GET /api/meals/serving-board` 老师分餐页（替代餐标记/家长确认时间/人工照护提示）
- `GET/POST /api/events`、`POST /api/events/{id}/messages`、`PUT /api/events/{id}/status` 协同事件
- `GET /api/timeline/child|class|event|parent` 时间轴；`GET /api/alerts`、`POST /api/alerts/{id}/handle` 异常预警

## 说明

- 人脸核验为流程留痕（记录核验方式与结果），不接入真实人脸库；证件号支持全号或后 4 位核验。
- 晨检同一儿童同日仅一条记录，重复提交为更新；事件/预警等联动仅在首次登记时触发。
- 过敏餐替换确认链为 厨房发起 → 保健老师 → 班级老师 → 家长 → 厨房出餐 → 班级分餐；家长确认前厨房不可出餐，家长未确认或任一环节拒绝时，分餐页对该儿童标红「人工照护 · 禁止发放常规餐」；出餐与分餐自动写入当日「用餐」照护记录与成长时间轴。
- 过敏源比对为规则匹配（常见过敏源关键词 × 儿童过敏档案 × 菜单/替代食材），替代食材仍含过敏源时平台拒绝提交。
